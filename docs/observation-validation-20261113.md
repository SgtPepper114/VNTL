## 结果适用范围

准确度来自固定的 20 张截图；逐字判稳来自五段开头字幕；接口耗时来自五次配对试验，受网络、上下文长度及服务负载影响。开头样本支持当前方案的可用性判断。后续游玩可继续覆盖其他字体、竖排文本、菜单、人物演出与字幕区域，并据此调整判稳参数和图标识别规则。

字幕区域选择影响可见文字范围；60% 适合本次底部对白，菜单和顶部字幕可使用 0%。新场景描述与正常预译并行，场景结果进入后续翻译上下文；疑难识字会等待视觉校验，因此耗时可高于普通本地识字路径。

## 闪烁字幕修复与稳定策略

实景诊断发现，结束标志的亮相位可由本地像素过滤识别，暗相位会被 OCR 读成额外的「。逐字完全一致的安静计时因此重复开始。模拟器底部状态栏也会进入原先的识字区域。

稳定策略参考 [GameSentenceMiner 的 TwoPassOCRControllerV2](https://github.com/bpwhelan/GameSentenceMiner/blob/main/GameSentenceMiner/ocr/gsm_ocr.py)，在 VNTL 中独立实现：结合正文相似、逐行文字框稳定、同页增长候选及 4 秒最长等待。VNTL 保留可配置的稳定等待时间，默认 600 毫秒；图框或超时触发的候选交给视觉模型校验。文字判断与原文输出分离，已有译文缓存跟随稳定后的页面身份。

字幕识别范围新增下边界，默认 100%。最初的隔离诊断使用上边界 60%、下边界 95%，用于区分对白闪烁与模拟器状态栏变化。正式方案采用下面的自动游戏画面标定，字幕区域默认覆盖标定后画面的 0%–100%。

## 通用游戏画面标定与全画面回放

首次选定窗口以及窗口尺寸变化时，截图模型返回归一化游戏画面矩形，后续截图在本地裁切。提示词保留游戏自身的菜单、HUD、对白和黑边，排除宿主菜单、工具栏和状态栏。响应使用严格 JSON 和边界校验，单次最多等待 12 秒；失败后使用完整窗口并显示提示。重新选择窗口或切换此设置可重新标定。

一次实际标定耗时 **1.668 秒**，将 1564×1310 的窗口裁为 `[0, 46, 1564, 1235]`。目视核对确认宿主菜单、状态栏已排除，场景与对白保留。相同区域的 29 帧整幅游戏画面 OCR 热运行中位耗时 **66.77 毫秒**、P95 **75.42 毫秒**；首次含模型初始化约 **1.575 秒**。这些数据来自当前录制样本，其他游戏边界和识字效果需要对应画面验证。

整幅游戏画面回放额外暴露出右上暂停图标被识别为独立 `!` 的情况。本页状态增加已确认文字框布局记忆：新布局先确认，已确认布局再次出现时复用稳定状态。清屏、新页或切换窗口后重置。视觉校验确认正文与同页缓存一致时，沿用已有译文。

| --- | ---: | ---: |

表中首次新暂停布局仍经过一次确认。离线服务测试的视觉接口原样返回本地识字结果，用于验证调度与缓存；识字准确性另由实际接口结果核对。

实际 API 链路的两次首次预译分别耗时 **6.69 秒、6.87 秒**，包含首次画面标定、冷启动 OCR、稳定等待、视觉校验和翻译。缓存就绪后的直接显示回调约 **0.008 毫秒**，仅反映内存与回调分发，手柄和 Qt 绘制耗时另计。后续出现暂停图标时，视觉校验确认正文相同，复用已有译文；随后三轮暗相位与暂停布局切换产生 **0 次新增 API 调用**。

实际识图仍出现一次低清假名读法差异：亮相位读为「キボ」，暗相位读为「キホ」，因此重新翻译一次。该试验的“所有原文完全一致”检查结果为失败，缓存循环检查通过；保留两类结果以区分识字误差和观察调度问题。

五段逐字字幕最终回放仍为 **5/5 完整触发**，最后文字出现至稳定事件 **0.792–0.876 秒**；此延迟按录像时间轴计算，OCR 推理和网络时间另计。最终 **316 项自动化测试通过**，包括标定失败回退、窗口变化和取消旧请求、同页缓存复用、真实追加文本重译以及设置保存／取消。

## 背景独立透明度修复

Windows 浮窗改为前景内容层与背景层分别渲染，背景滑块仅控制字幕底色。前景采用近黑色键，文字与按钮保持固定的渲染颜色；顶部控制栏和缩放柄保留完整命中区域。背景为 0% 时仍可从顶部拖动浮窗并打开设置，背景可见时空白区域的拖动及右键操作转交主浮窗处理。

本机 200% DPI 下对真实 `OverlayWindow` 做原生合成验证：背景 alpha 0、128、255 时，**71,665 个前景像素全部保持一致**，其中含 4,301 个亮色文字像素；零透明度处显示底景，完全不透明时显示配置的背景色。两层窗口均成功应用截图排除，截取像素恢复为底景，前台焦点保持原状。

颜色选择器与透明度滑块同步，保留颜色选择器的精确 alpha；设置取消恢复修改前外观。Windows 原生透明设置失败时恢复普通窗口样式，维持文字和控件可见。此版本 **326 项自动化测试通过**。

## 2026-11-14：标定恢复与 HTTPS 直连

日志确认模型请求出现 `APIConnectionError`，首次标定失败又被缓存为该窗口尺寸的永久结果。标定现在按 5、15、30、60 秒间隔后台重试，后续间隔保持 60 秒；普通翻译键可提前触发。重试期间本地观察继续进行，成功后在最新截图上应用边界并清理旧几何下的缓存。代理及证书环境变化时刷新 API 连接，正在执行的旧请求完成后再关闭旧连接。

独立实验主动让首次标定返回失败，5 秒后交给真实 API。请求期间采样帧数由 26 增至 32，随后获得有效边界、完成一次翻译并显示，失败提示清除。此试验使用录制截图与独立内存，首次失败为测试注入。

直连证书对照使用相同的 `https://api.deepseek.com/models`，全部绕过 HTTP 代理且保留验证：默认 certifi 信任库报 `SSLCertVerificationError` 代码 19；Windows 系统信任库与 truststore 均获得 HTTP 401，表明 TLS 握手与 HTTP 访问成功。直连叶证书的签发者为 `Kaspersky Anti-Virus Personal Root Certificate`，域名为 `api.deepseek.com`。本机 Windows 已信任该安全软件证书，SDK 的独立 certifi 证书包未包含它。

Windows API 连接改用局部 truststore 上下文，通过系统证书库验证；域名校验与 `CERT_REQUIRED` 保持开启。显式 `SSL_CERT_FILE` / `SSL_CERT_DIR` 延续 HTTPX 原优先级，代理及 `NO_PROXY` 继续按环境生效。实现参考 [HTTPX SSL 指南](https://www.python-httpx.org/advanced/ssl/) 与 [truststore 文档](https://truststore.readthedocs.io/en/latest/)。

生产 SDK 的进程内直连试验设置 `NO_PROXY=*`，确认代理 transport 数为 0。真实翻译耗时 **0.755 秒**，真实游戏画面标定耗时 **0.799 秒**。最终 **354 项测试通过**；安装包已包含 `tls_client`、`truststore._api` 和 `truststore._windows`。已启动的打包实例随后也成功完成一次 DeepSeek 摘要请求，HTTP 200。
